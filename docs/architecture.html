自律ペンテストエージェント
アーキテクチャ & 設計

小型ローカルモデルを中央 Model Service 経由で使い、標的を 偵察 → 攻略 → フラグ提出 まで自走させる harness。層を分離し、未確定な API 仕様は環境変数とインターフェースの裏に閉じ込めてある。

そもそも何をするのか

「標的サーバを自分で攻略してフラグ（秘密の文字列）を盗むAIプログラム」を作る競技。 人間は標的に一切触らない。人間が作るのは、攻略を自動でやるエージェントの方。 CTFプレイヤー（ハッカー）が手でやる動きを、まるごとプログラムにやらせ、その頭脳にLLMを使う。

当日の流れ具体的に何が起きるか
1. 提出エージェント一式を Docker イメージに固めて主催にアップロード
2. 起動主催の隔離環境（サンドボックス）でエージェントが動き出す
3. 攻略自力で 偵察 → 攻略 → フラグ発見（標的サーバに接続して弱点を突く）
4. 提出見つけた flag{…} を提出APIにPOST ＝ 得点
5. 完了完了通知を出す。数分でスコアとログが出る
6. 反復ログを見て改善 → 再ビルド → 再投入を会期中に繰り返す

なぜ難しく、何で勝つのか: 使えるのは小さいオープンソースLLMだけで、 小さいモデルほど高得点。だから勝負は「賢いモデルを持ってくる」ことではなく 「そこそこのモデルを巧い土台（harness）で賢く動かす」こと。さらに速く解くほど高得点（decay）。

勝ち筋（リーダーボードの実況から）: 上位は薄く、数問確実に解くだけでトップ10に入れる。 ただし 「CAUGHT BY SOC」＝検知されると大幅減点（総当たり・騒がしい挙動は自滅、マイナス点も出る）。 → 静かに・最小手数で・確実に取る agent が勝つ。この方針を runner とツールに組み込んである。

01

前提となる用語（ゼロから）

各用語を「一言 / なぜ必要 / このプロジェクトでは具体的に」の3点で。

OCIコンテナ / Docker イメージ packaging/

一言
アプリと必要なもの一式（Python・ライブラリ・自分のコード）を丸ごと固めた「持ち運べる箱」。
なぜ
手元で動いたものを主催サーバでも寸分違わず同じに動かすため。「自分の環境では動いた」を無くす。OCIはその箱の標準規格名（≒Dockerイメージ）。
具体
python:3.11-slim に halctf/ を入れ、docker save で .tar にして提出。モデル本体は入れない（推論は中央）ので2.5GBに軽く収まる。

中央 Model Service / OpenAI互換API client/

一言
主催が用意した「LLMに質問を投げる窓口」（サーバ）。
なぜ
全員が各自GPUを持つのは無理。共通窓口にHTTPで質問して返事をもらう。手元にGPUもモデルも要らない。
具体
POST /chat/completions にメッセージを送ると返事が返る。形がChatGPTのAPIと同じ（＝OpenAI互換）なので既存の作法が流用できる。使うモデルは model フィールドで指定。

具体 — model query（LLMに一回質問する）

// リクエスト: エージェント → 中央 Model Service
POST /chat/completions
{
  "model": "Llama-3.2-3B",        // 小型ほど高得点
  "messages": [
    {"role":"system","content":"あなたはCTF攻略エージェント…"},
    {"role":"user","content":"この標的のフラグを取って"}
  ],
  "tools": [ /* 下の tool-calling で説明 */ ]
}

// レスポンス: モデルの返事（文章ではなく「道具を呼びたい」指示）
{ "choices":[{ "message":{
    "tool_calls":[{"function":{
      "name":"recon", "arguments":"{\"target\":\"default\"}" }}]  // ← 次の手
}}]}

LLMのツール呼び出し（tool-calling） tools/

一言
LLMに「使える道具のリスト」を渡すと、文章の代わりに『この道具をこの引数で呼んで』という機械が読める指示を返す仕組み。
なぜ
LLMは文章を作るだけで自分でHTTPを送れない。「recon を呼びたい」と言わせ、実際に実行するのはこちらのコード。結果を返す→次の手を言わせる、の繰り返し。
具体
実CTF用の道具は3つ: read_env（env のフラグ／Flag 1）・http_get（web 標的／Flag 2,3）・flag_submit（提出）。LLMが flag_submit(flag="flag{…}") を返したら、こちらが本当に sidecar /submit へ POST する。

エージェント / harness （リポジトリ全体）

一言
エージェント＝目的を与えると自分で考え行動を繰り返すプログラム。harness＝それを成り立たせる枠組み一式。
なぜ
作るのは「賢いモデル」ではなく、借り物モデルを手足（ツール）と頭の使い方（ループ）で賢く働かせる枠組み。
具体
このリポジトリ全体が harness。モデルは借り物、勝敗は harness の設計で決まる。

決定ループ / ReAct loop/react.py

一言
「観察→考える→動く→また観察」を繰り返す仕組み。ReAct（Reason+Act）はその代表型。
なぜ
CTFは一撃では解けない。偵察の結果を見てから次の手を決めるを繰り返す。1回のLLM質問では足りない＝だからループする。
具体
while ループで、1周＝「LLMに1回聞く」＋「ツールを1回実行」。最大20周（max_steps）。

具体 — ループの心臓部（簡略）

while step < max_steps:
    result = client.chat(state.build_messages(), tools=specs)  # ① LLMに聞く
    for tc in result.tool_calls:                    # ② LLMが選んだ道具を
        obs = registry.get(tc.name).run(tc.arguments, ctx)  # ③ 実際に実行
        state.add(observation)                      # ④ 結果を記録し次の周へ
        if obs.done: return solved                  # フラグ受理で完了

なぜループが要るか: recon の所見「path-traversal の気配」を見てから exploit の手法を決めるので、最低でも複数周が必要。

フラグ / 提出 / 完了通知 services/sidecar.py

フラグ
flag{something_secret} のような秘密の文字列。標的を攻略するとレスポンスやファイルから手に入る「攻略できた証拠」。
提出
sidecar に POST /submit {challenge_id, flag}（または MCP submit_flag）。これが得点行為。
完了通知
POST /done で早期終了しキュー枠を解放。出さないとリソースを無駄に握る。

sidecar / 実行アイデンティティ 127.0.0.1:9000

一言
自分の Pod に同居する中継役（NGINX）。agent は外部と直接話さず全部これ経由。
なぜ
ネットワークを隔離しつつ、推論・提出・アイデンティティ注入を一点で担う。
具体
実行時に OPENAI_BASE_URL／MCP_ENDPOINT／HAL_* が env として注入される。我々は読むだけ（自分で export すると自分の agent を壊す）。

MCP（Model Context Protocol）サーバ services/mcp.py

一言
チャレンジ情報とフラグ提出の窓口。MCP_ENDPOINT にある。
なぜ
「どんな問題があるか／説明／提出／ヒント」を得る標準インターフェース。
具体
JSON-RPC の tools/call で list_challenges / get_challenge / submit_flag / request_hint 等を呼ぶ。ワイヤ形式は現地で要確認（1ファイルに閉じ込め済み）。

起動要件（USER ID / heartbeat） runtime.py

USER ID
起動30秒以内に USER ID: <uid> を stdout 出力（本人確認の lint ゲート）。
heartbeat
stdout 無音2分でハング扱い。定期出力し続ける。出力は必ず flush。

検知回避（"CAUGHT BY SOC"） runner.py

一言
標的への騒がしい挙動・総当たり提出は検知され減点される（マイナス点も出る）。
具体
誤提出は上限（既定3）で打ち切り、標的アクセスは間隔を空け、易しい確実な問題から静かに取る。

recon / exploit（偵察 / 攻略） tools/recon.py · exploit.py

recon
標的を調べる。どんなサーバか、どんなURL/ポートがあるか、怪しい入力欄はどこか。攻める前の下調べ。
exploit
見つけた弱点を実際に突く。

具体 — Web標的の例（本プロジェクトのモックと同じシナリオ）

# recon: name パラメータでファイルを読めそう、と気づく
GET /files?name=readme        → 200 "This is the readme."

# exploit: パストラバーサルで本来読めないファイルを読む
GET /files?name=../../flag.txt → 200 "flag{path_traversal_win}"   ← 発見！

小型モデル / モデル多段 HALCTF_MODEL_CHAIN

小型
パラメータが少ないLLM（3B〜7B等）。速く軽いが賢さは劣る。競技では小型ほど高得点なので、まず小型で挑む。
多段
まず最小で挑戦し、詰まったら一段大きいモデルへ切替。Llama-3.2-3B,Qwen3.5-4B,gpt-oss-120b の左が最優先。
02

全体像 — 層 + 外部境界（すべて sidecar 経由）

エージェントは「頭脳（決定ループ／runner）」「道具（ツール）」「外界との口（クライアント／services）」に分かれる。実仕様では agent は sidecar（127.0.0.1:9000）としか話さない。sidecar が推論・チャレンジ探索/提出・標的サブネットを振り分ける。外部依存はこの1点に集約され、すべて env で差し替えられる。

用途我々のコード経路
推論（次の手を聞く）client/OPENAI_BASE_URL → sidecar /llm → Model Service
チャレンジ探索・ヒントservices/mcp.pyMCP_ENDPOINT → sidecar /mcp
標的の偵察・攻略tools/http_get.py現CTFのサブネット（sidecar 経由）
フラグ提出・完了services/sidecar.pyPOST /submit ・ POST /done
03

各層の責務

層を分けたのは、チームが並行作業でき、当日は層単位で差し替えられるようにするため。各層は隣の層のインターフェースだけを知っていて、実装の中身には依存しない。

client/

クライアント層

OPENAI_BASE_URL を OpenAI 互換で叩く（api_key="not-needed"）。小型優先→難所でフォールバックのモデル多段を chat() に隠蔽。

  • リトライ / タイムアウト
  • Mock 実装で外部不要の検証
tools/

ツール層

LLM が選んで呼ぶ道具。誤選択を防ぐため3つに絞る（実CTF用 web_registry）。

  • read_env — env のフラグ
  • http_get — web 偵察・攻略
  • flag_submit — 提出（誤提出上限で打切り）
loop/

決定ループ層

観測→思考→ツール選択→実行の ReAct。状態を外部保持し履歴を全部渡さない。ループ検出を担う。

services/

services 層

プラットフォーム接点。McpChallengeService（探索）＋ SidecarClient（/submit・/done）＋ MockPlatform を差し替え。

runtime · runner

ランタイム / ランナー

runtime.py: USER ID 出力・heartbeat。runner.py: 起動→探索→各チャレンジ ReAct→done と検知回避の方針。

config/ · packaging/

設定 / パッケージング

注入 env（無印優先）＋ローカル上書き（HALCTF_）。Dockerfile（-u）→ tarball（2560MB 検査）。

04

決定ループ — ReAct と終了条件

1ターンごとに「状態を組む→LLM に推論させる→ツールを実行→観測を状態へ」を回す。小型モデル対策として、毎ターン全履歴は渡さず直近＋要約だけを渡す。4つの終了条件のいずれかで completion signal を出して run を締める。

05

1 run のシーケンス — モックで実測

モック標的で実際に走らせた流れ。エージェントの手数は recon → exploit → flag_submit の3手。偵察の所見から攻略手法を選び、応答からフラグを抽出して提出、最後に完了通知を出す。

06

未確定を止めなかった抽象化（確定後の結線）

ループとツールはインターフェースにしか依存せず、実装が本物かモックかを知らない。だから仕様確定前も Mock で開発でき、確定後は実装を差し込むだけで済んだ。切替は env（HALCTF_USE_MOCK）一発。

07

小型モデル最適化の設計判断

「小さいモデルほど高得点／速さ＝得点」という競技の核に合わせた設計判断。それぞれが具体的なコードに落ちている。

モデル多段

小型優先で通し、難所だけ中型へフォールバック。HALCTF_MODEL_CHAIN の左が最優先。加点式が確定したら切替閾値に反映する。

コンテキスト圧縮

小型モデルは長文脈に弱い。状態を外部保持し、履歴が伸びたら古い部分をローカル要約に畳んで直近だけ生で渡す（state.build_messages）。

ツールを絞る

選択ミスを減らすため MVP は 3 ツールだけ。説明文は短く明快に。shell 等は制約確定後に足す。

ループ検出

同一の手（ツール名＋引数）が連続したら打ち切る。同じ手を繰り返してトークンと時間を浪費しない。

誤提出の抑止

提出前にフラグ正規表現で検証。誤ったフラグ提出でスコアや試行を浪費しない。

環境非依存

エンドポイント・モデル・フラグ形式は全て env。提出方式や環境が変わっても同じコードで動く。

08

リポジトリ構成と動かし方

halctf/
├─ config.py          # 注入 env（無印優先）+ ローカル上書き（HALCTF_）
├─ runtime.py         # USER ID 出力 + heartbeat
├─ runner.py          # 起動→探索→各チャレンジ ReAct→done + 検知回避
├─ client/            # OPENAI_BASE_URL への口（base/openai_compat/mock）
├─ tools/             # read_env / http_get / flag_submit（実）, recon/exploit（demo）
├─ loop/              # react.py（ReAct）+ state.py（圧縮）
├─ services/          # mcp.py（探索）+ sidecar.py（/submit,/done）+ mock.py + base.py
└─ cli.py             # --demo / --smoke / 実行
spec/      # API 仕様メモ（実仕様で更新）
packaging/ # Dockerfile（-u）+ build.sh（save→tarball, 2560MB検査）
examples/  # mock_target.py（ローカル検証用の標的）
tests/     # config / services / tools / loop / runner / state（27件）

# 動かす
make dev      # 依存インストール
make test     # 27 件のテスト
make demo     # モックで 1 問を自力で解く → solved: True
python3 -m halctf.cli --smoke   # 実サービスへの提出パイプライン疎通確認
make build    # OCI イメージ → tarball
